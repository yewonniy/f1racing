### **기능 1: 드라이버/팀 정보 페이지** ✅

- 구현
    
    **드라이버/팀 정보 + 경기 결과 업데이트**
    
    구현:
    - F1 공식 API에서 경기 결과 수집 (매 경기마다) 
    - PostgreSQL에 저장 → **RDS**
    - 간단한 REST API로 조회 가능 → **Redis**
    
    ### 드라이버 및 팀 정보
    
    [동작 흐름]
    
    1. 드라이버 정보는 자주 안 바뀌니까 Redis에 TTL 1시간으로 캐싱
        1) 드라이버 이름
        2) 드라이버 번호 (막스 33)
        3) 소속 팀
        4) 현재 순위
        5) 현재 포인트
        6) 국적
    2. 사용자 즐겨찾기는 RDS에 저장
    3. 첫 요청 시만 F1 API 호출, 이후 Redis에서 반환
    
    ```jsx
    // 드라이버 정보는 자주 안 바뀌니까 캐싱
    // F1 API → Redis → 클라이언트
    
    // 요청시 : Redis 확인 (있으면 바로 반환) 없으면 RDS 조회 -> RDS를 Redis에 캐싱 후 반환
    1번째 요청: F1 API 호출 (800ms) → Redis 저장
    2번째 요청: Redis에서 가져옴 (1ms)
    3번째 요청: Redis에서 가져옴 (1ms)
    ...
    
    → API 호출 90% 감소
    → 응답 속도 75% 개선
    ```
    ```
    
    [왜 이렇게?]
    
    - 드라이버 정보는 시즌 중 거의 안 바뀜
    - Redis로 응답 속도 70% 개선
    - 사용자별 커스터마이징은 RDS 활용
    
    ⇒ 구현 내용 : 드버 프로필 및 통계(순위 순으로 보여주기), 팀 정보, 사용자 즐찾 기능?
    
    ---
    
    ### 경기 결과
    
    [동작 흐름]
    
    1. 레이스 끝난 후 결과는 RDS에 영구 저장
    2. 최근 N개 레이스는 Redis 캐싱
    3. 통계 계산 결과도 Redis 캐싱
    
    [왜 이렇게?]
    
    - 과거 데이터는 영구 보관 필요 (RDS)
    - 자주 조회되는 데이터는 캐싱 (Redis)
    - 복잡한 통계 계산은 한 번만 하고 캐싱
    
    구현 내용 : 레이스별 결과
    
    

### **기능 2: 경기 중 실시간 순위 (WebSocket)** ✅✅

- 구현

    구현:
    ~~- F1 API polling (5초마다 순위 갱신)~~
    - **WebSocket**으로 클라이언트에 실시간 브로드캐스트
    - **Redis**에 현재 순위 캐싱
    - 간단한 웹 프론트 (Vue.js 또는 React)
    
    이유: "대규모 트래픽"의 핵심이 이 부분
    
    [동작 흐름]
    
    1. F1 API에서 1초마다 레이스 데이터 가져옴
    2. Redis에 캐싱 (TTL 5초)
    3. WebSocket으로 연결된 모든 클라이언트에게 브로드캐스트
    
    ⇒ Locust로 검증해서 동접 500명 처리 가능했다는 거! 검증할 것!!
    
    [왜 이렇게?]
    
    - F1 API 호출 제한 회피 (Redis 캐싱)
    - 여러 사용자가 동시에 봐도 API 1번만 호출
    - WebSocket으로 실시간 업데이트
    
    ⇒ 구현 내용 : 드버 현재 순위, 랩 타임 실시간 표시, 피트스탑 정보, Fastest 드버, 타이어 상태
